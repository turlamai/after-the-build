# 数据可能丢失，程序怎样继续通信

我们希望申请者发送姓名，报名服务收到完整信息后完成登记。但 IP 网络可能丢弃数据，也可能使不同数据包以不同顺序到达。

如果每个应用都必须自己设计一套处理这些情况的机制，开发会变得困难。

于是，在 IP 提供的通信基础之上，人们建立了为应用提供不同传输能力的协议。这一层通常称为传输层（Transport Layer）。

## TCP 提供有序的字节流

传输控制协议（Transmission Control Protocol，TCP）提供面向连接、可靠且有序的字节流传输能力。

我们可以先理解一个基本机制：发送方为发送的数据维护序号，接收方通过确认信息告知已经收到的连续数据范围。发送方在适当条件下重新发送尚未得到确认的数据。

接收方可以根据序号处理重复和乱序数据，使应用按顺序读取字节。

![丢失数据经重传后形成有序交付](../assets/intro-tcp-retransmission.svg)

真实 TCP 还包含流量控制、拥塞控制、连接状态等机制。图中不模拟完整的确认与重传算法。

可靠传输也不是无限保证。如果网络长期中断，连接仍可能失败。应用必须能够处理超时、断开连接和不完整业务操作。

## TCP 没有自动保留业务消息边界

如果程序先写入文字 ABC，再写入 DEF，接收方不一定恰好先读到 ABC、再读到 DEF。

TCP 为应用提供字节流。读取结果可能因缓冲和实际读取方式而分成不同长度，但成功交付的字节顺序仍应一致。

如果业务需要区分两条消息，就需要协议规定消息长度、分隔符或其他可以识别边界的方法。

这与第一章的编码原则一致：接收者必须知道如何解释得到的数据。

## UDP 提供另一种传输方式

用户数据报协议（User Datagram Protocol，UDP）提供数据报形式的传输。

发送方交给 UDP 的数据报具有边界；接收方如果成功接收相应数据报，可以按照数据报处理它。但 UDP 本身不提供 TCP 那样的可靠、有序交付机制，也没有相同的连接建立过程。

这并不意味着 UDP 一定更适合实时应用，也不意味着使用 UDP 就不能实现可靠传输。应用或建立在 UDP 之上的其他协议可以根据需求提供额外机制。

## 为什么不同业务选择不同传输方式

传输文件时，缺少一个字节都可能使结果不正确。某些实时音视频场景则可能更加关注延迟，而不愿为了过时的数据无限等待。

选择协议需要理解业务对完整性、顺序、延迟和错误处理的要求。

即使 TCP 已经成功交付请求，仍然不能证明报名已经写入持久化存储。网络传输成功和业务执行成功是两个不同层次的事实。
