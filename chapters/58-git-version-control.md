# 为什么不能靠复制文件来管理软件版本

假设我们先完成报名功能，再增加取消报名。如果第二次修改发生错误，希望恢复先前正确的代码。

可以复制一个项目文件夹作为备份，但如果多人同时修改许多文件，仅靠文件夹名称很难回答：谁改了什么？这些修改基于哪个版本？哪些修改应该一起保留？

版本控制系统（Version Control System）用于记录和管理文件内容的演变。Git 是一种广泛使用的分布式版本控制系统。

## 提交记录一个项目状态

Git 仓库（Repository）保存项目文件的版本历史及相关管理信息。

一次提交（Commit）记录项目中被纳入该次提交的文件状态、相关元数据以及与已有历史的关系。它可以通过提交标识进行引用。

工作目录中的修改并不会自动成为提交。Git 使用暂存区（Staging Area）组织下一次准备提交的内容。

## 在自己的实验目录操作一次

在已经安装 Git 的电脑中，创建一个新的空实验目录，并进入该目录。不要在不了解状态的现有项目中照搬实验。

```sh
git init
git status
```

创建一个内容为「报名活动」的 README.md 文件，然后执行：

```sh
git add README.md
git diff --cached
git commit -m "Add registration description"
git log --oneline
```

git add 选择准备纳入下一次提交的内容。git diff --cached 显示暂存的修改。git commit 创建提交。如果没有配置提交身份，Git 可能要求先完成相关配置。

git log 显示历史。实际提交标识由 Git 生成，不需要与书中的示例一致。

## 为什么需要分支

当我们希望在保持现有可用版本的同时开发新功能，可以创建分支（Branch）。

Git 分支本质上是可以随着开发移动的提交引用，不是必须复制出一套独立文件夹。

![从共同提交开始的两条开发历史](../assets/intro-git-branches.svg)

合并（Merge）用于组合不同开发历史中的修改。如果不同修改无法自动协调，Git 会报告冲突（Conflict），需要开发者根据真实需求决定最终内容。

没有发生文本冲突，也不代表功能必然正确。两个人可能修改不同文件，却共同破坏同一项业务约束。因此，合并后仍然需要测试。

## Git 和 GitHub 不是什么关系

Git 可以完全在本地工作。GitHub 是提供远程仓库托管及协作功能的平台之一。

将本地提交传送到远程仓库通常称为推送（Push）；从远程取得提交涉及获取（Fetch），将取得的变化进一步整合到当前工作则可以通过相应 Git 操作实现。

拉取请求（Pull Request，PR）是 GitHub 等平台提供的一种提出合并变更、讨论及审查代码的协作方式。创建 PR 不等于变更已经进入正式分支。

Git 可以记录源代码历史，但不能替代数据库备份，也不应把生产凭据或用户个人资料提交到普通代码仓库。
