# 为什么一个网站背后可能有许多台机器

假设报名服务已经可以正确处理请求，但是访问高峰时响应变慢。我们应该增加服务器，还是修改程序？

## 先确定瓶颈

响应变慢可能来自 CPU、内存、数据库、网络或其他等待。如果瓶颈是一条低效的数据库查询，增加后端实例不一定有效，还可能增加数据库压力。

提高单个实例的资源能力称为纵向扩展（Vertical Scaling）；增加运行实例的数量称为横向扩展（Horizontal Scaling）。

选择需要建立在实际测量上。

## 多个实例怎样共享入口

假设我们启动三个相同版本的报名后端。客户端不需要知道究竟连接了哪台机器。

可以设置一个组件，按照适当规则将连接或请求转发给后端实例。这种机制称为负载均衡（Load Balancing）。

![负载均衡将请求交给可用后端](../assets/intro-load-balancer.svg)

负载均衡可以在不同协议层工作，并不必然逐个 HTTP 请求分配。常见方案还包含健康检查，以判断后端是否能够承担新的工作。

但增加实例会引入共享数据问题。若每个进程分别保存报名人数，就无法保证三个实例遵守同一个容量限制。需要把权威数据交给所有实例共同使用的数据存储，并利用事务和约束协调修改。

不将处理后续请求所必需的状态仅保存在某个不可替换实例中的设计，通常更容易横向扩展。这就是无状态服务（Stateless Service）的一项重要思想。无状态不是系统完全不保存数据。

## CDN 解决什么问题

假设许多用户需要下载同一张活动介绍图片。每次从远端源服务器获取可能增加等待时间及源服务器压力。

内容分发网络（Content Delivery Network，CDN）可以通过分布在不同网络位置的节点提供内容访问能力。对适合缓存的内容，边缘节点（Edge Node）可以直接提供已有副本；需要时再向源站（Origin Server）取得内容。

![缓存命中与未命中的访问路径](../assets/intro-cdn-cache.svg)

CDN 不仅限于静态文件分发，但也不能盲目缓存所有内容。带有私人报名信息的响应必须按照正确的授权及缓存控制规则处理。

负载均衡与 CDN 解决不同但可能重叠的问题。理解机制比记住某个云产品名称更重要。
