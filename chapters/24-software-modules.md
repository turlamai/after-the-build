# 为什么不能把所有代码写在一起

一个只有十几行的报名程序可以放在同一段代码里。但真实的软件很快就会增加姓名检查、名额限制、取消报名、记录导出和界面显示等功能。

如果这些规则都混在一起，修改一种功能时就可能意外改变另一种功能。

我们需要为软件的不同部分建立清晰的职责。

## 将相关规则组织在一起

假设我们先把报名人数检查和更新放在一个函数中，再把显示结果放在另一个位置。

当我们把若干相关的函数、数据及其他定义组织成可单独使用的程序单元时，可以称其为模块（Module）。具体语言对模块的组织方式不同，有的使用独立文件，有的提供其他形式。

在 Python 中，一个常见办法是把报名规则放在 registration.py，再在其他文件中导入需要的函数。

registration.py 的内容可以是：

```text
def register(total, registered):
    if registered >= total:
        return registered, False
    return registered + 1, True
```

另一个文件可以通过 from registration import register 使用它。这是跨文件的教学示例，若要执行，应把两个文件保存在同一测试目录，并使用 Python 运行调用方。后续会通过完整项目验证这种组织方式。

## 调用者需要知道什么

假设界面只需要调用 register，提供总名额和已报名人数，再取得新的人数和是否成功的结果。

界面并不需要知道函数内部是先比较人数，还是先计算剩余名额。只要它能够依照约定使用函数，就能与这个模块协作。

一项软件功能对外提供的使用方式称为接口（Interface）。

如果我们约定函数的名称、参数、返回值、失败条件以及必要的数据限制，就建立了一份调用契约（Contract）。

应用程序编程接口（Application Programming Interface，API）是软件向其他程序部分提供的可调用能力与相关约定。它可以是本机的函数接口，也可以是通过网络使用的服务接口。API 并不专指 HTTP 接口。

## 接口约定还必须描述失败情况

例如 register 接收两个整数，返回新人数及是否成功。我们还必须规定总名额是否允许为负数、已报名人数能否大于总名额，以及非法输入应该如何报告。

如果只写出函数名称，而没有规定这些条件，两位开发者可能分别实现出不同的行为，却都认为自己遵守了接口。

一个完整的接口通常需要说明输入、输出、错误条件与副作用。副作用（Side Effect）是指除了返回结果以外还改变外部状态的行为，例如修改文件或数据库记录。一个只计算剩余名额的函数和一个实际保存报名记录的函数，不能因为都返回人数就视为具有相同契约。

## 用一个小实验检查模块边界

```python
def register(total, registered):
    if not 0 <= registered <= total:
        raise ValueError("invalid capacity")
    if registered == total:
        return registered, False
    return registered + 1, True

assert register(20, 19) == (20, True)
assert register(20, 20) == (20, False)
try:
    register(20, 21)
except ValueError:
    pass
else:
    raise AssertionError("invalid input must be rejected")
```

该教学函数只接受符合约定的整数，并检查数值范围；它没有执行完整的运行时类型检查，也没有保存记录。界面或网络层需要按照自身边界补充输入验证。

这样组织代码，可以先在没有界面和数据库的情况下检查核心计算，再针对实际数据保存与交互进行其他测试。

## 为什么接口需要稳定

如果我们把 register 的返回值从两个结果变成一个字符串，调用它的界面代码可能无法继续正确工作。

这种现象解释了为什么软件更新不能只关注新功能有没有实现，还要考虑已有使用者是否能够继续使用原来的接口。

当内部实现发生改变，而符合旧契约的调用者仍能够继续正常工作时，我们通常称之为保持向后兼容（Backward Compatibility）。

但兼容性需要明确范围：保证函数调用形式兼容，不一定意味着保存的数据格式也兼容。

## 减少不必要的依赖

假如报名规则直接调用某种窗口工具，那么当我们希望通过命令行处理报名时，就可能被迫一起引入图形界面。

更合理的设计通常是让业务规则独立于具体界面，界面通过约定接口使用它。

这种设计有助于实现关注点分离（Separation of Concerns）：不同部分承担不同职责。

模块并非越多越好。拆分应当服务于理解、变化和测试，而不是为了得到大量很小的文件。下一章我们会进一步讨论，为什么大量常用模块不必由每个开发者重新编写。
