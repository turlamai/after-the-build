# 怎样判断 Agent 的工作是不是真的完成了

我们已经了解模型、上下文、检索、工具调用和执行环境。现在可以将这些知识用于一项实际开发任务。

假设要求 Agent 增加取消报名功能。我们需要让它知道规则，还要知道什么证据能够证明功能实现正确。

## 任务描述应包含可以验证的要求

例如：

```text
目标：为现有报名应用增加取消报名功能。
前置：先读取当前接口、数据库结构与已有测试。
要求：
- 只能取消当前账户有权管理的报名记录。
- 成功取消后释放一个名额。
- 重复取消不得重复释放名额。
- 原有报名容量限制继续成立。
验收：新增自动测试，运行相关测试并报告结果。
限制：不修改生产数据，不直接发布生产环境。
```

这段描述之所以有用，是因为前面各部已经解释过授权、数据库事务、幂等性、自动测试和生产环境等术语。

专业词汇能够帮助我们准确表达技术要求，但如果缺少相应理解，使用术语并不会自动使要求正确。

## 将模型陈述和外部证据分开

Agent 可能说已经修复问题。我们可以进一步检查：

| 陈述 | 可以要求的证据 |
|---|---|
| 已修改代码 | 实际文件差异或提交 |
| 测试通过 | 测试命令、退出状态、测试结果 |
| 已提交 | 仓库中的提交标识及内容 |
| 已发布 | 目标发布物或部署记录 |
| 服务正常 | 实际业务检查及运行指标 |

证据本身也需要检查适用范围。例如，仅有单元测试通过，不能证明实际生产数据库中的并发行为正确。

## 外部内容不能擅自扩大任务权限

Agent 可能从网页、文档或工具结果中读到要求它执行其他操作的文字。

如果系统不能正确区分用户授权、宿主规则和外部数据，就可能受到提示注入（Prompt Injection）影响。

外部内容即使使用命令式语气，也不因此获得执行权限。应结合可信指令来源、工具访问限制、必要的人工授权及实际验证进行控制。

不能仅依靠一条提示词保证所有风险消失。

## 成本也需要可观察

一次任务可能包含许多模型请求、工具调用和构建操作。成本不只来自用户最初输入的文字。

假设某次教学任务使用虚构单价，每百万输入 Token 2 元，每百万输出 Token 8 元。累计输入 100000 Token，输出 25000 Token，则模型费用为 0.4 元。

实际服务可能采用不同计费方式，还可能存在缓存、工具、存储及运行环境费用。本例不是任何真实产品的报价。

应根据任务价值、验证要求和实际资源使用量设置合理预算，而不是无限制地延长执行过程。

## 从使用 AI 走向拥有产品

至此，我们已经拥有理解 Agent 工作机制的基础。真正有价值的能力并非记住某个工具界面的操作，而是能够把需求描述清楚、选择适当环境、理解模型和工具的边界，并验证实际交付结果。
