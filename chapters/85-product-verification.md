# 怎样证明这个应用满足了最初的要求

在 examples/registration 目录运行：

```sh
python3 -m unittest -v
```

测试在独立临时目录中建立数据库，不操作正常运行时的数据库文件。

## 不仅检查正常情况

测试覆盖合法报名、容量限制、非法姓名、重复请求标识、请求内容冲突以及重新打开数据库后的记录保存。

并发测试先建立 19 条记录，再通过两个线程同时尝试提交不同请求，最后检查成功数量和最终数据库记录数。

HTTP 测试启动只监听本机临时端口的实验服务，验证 JSON 请求与响应，并在测试结束后关闭服务。

![从需求到业务测试和 HTTP 测试](../assets/intro-product-verification.svg)

这些测试的目标是形成可以重复取得的证据，而不是让开发者仅凭界面正常就宣布项目完成。

## 用失败输入及重复请求验证接口边界

除了普通成功请求，还应检查错误的 Content-Type、无效 JSON、非对象 JSON、超出长度限制的请求体及不存在的路径。每次失败后都需要确认记录没有增加。

同一个请求标识也可能由两个线程同时提交。测试应检查只有一条记录被创建，两次合法请求获得相同编号。不同请求标识竞争最后一个名额则应只有一个成功。

满员之后仍应允许已成功请求的合法重试得到原有结果，因为这不是新的报名。这样的检查可以发现错误的判断顺序，例如先检查容量再查询请求标识。

测试代码只能证明运行过的具体情形；它不能替代完整故障分析。

## 怎样理解测试结果

测试通过意味着本次运行覆盖的条件得到了验证。它不意味着软件已经满足所有可能的生产要求。

例如，本项目不验证跨设备公网通信、身份认证、真实用户数据保护或大规模负载。它也不能用一次并发测试证明任意环境下的所有并发情况都已正确处理。

如果让 AI 修改这个项目，应要求它说明改动依据、保留现有测试、补充新增行为的测试，并报告实际执行结果。

## 发布之前还缺什么

真实产品需要明确使用者身份、取消报名及重复人员规则，补充安全设计、正式服务运行环境、HTTPS、备份与恢复、监控和维护流程。

每项新增要求都需要对应实现及验收证据。不能因为这个教学项目可以运行，就把它描述成可直接使用的商业服务。
