# 数据已经保存，为什么还要备份

上一章已经知道事务可以提交或回滚。现在假设数据库告诉我们报名成功，是否就意味着这些数据永远不会消失？

并不意味着。持久性和备份处理的是不同范围的问题。

## 从内存中的修改到持久化结果

在修改数据时，数据库可能先在内存中处理相关内容，再按照自己的存储机制将信息写入持久化设备。

许多数据库使用预写日志（Write-Ahead Log，WAL）等机制。在采用这种机制的系统中，数据库按照规定先持久化足以用于恢复的日志信息，再允许相应的数据页修改进入持久化存储。

发生异常退出后，系统可以利用已经保存的信息恢复到符合事务规则的状态。

不同数据库的日志、检查点及恢复方式并不完全一样。有些系统使用其他机制。提交时的持久性保证还受到配置、操作系统及设备行为影响。

数据库报告事务成功，不等于物理设备永远不会损坏。

## 日志与数据页怎样配合

数据库通常把存储组织为若干数据页（Data Page）。修改一条记录可能涉及数据页、索引及其他内部结构。如果设备在这些修改全部持久化之前发生故障，就需要一种恢复到有效状态的机制。

对于采用传统重做型预写日志的系统，可以用以下简化顺序理解一次修改：先准备恢复所需的日志记录；按照数据库要求使相关日志达到规定的持久化条件；再允许相应的数据页写入；在满足提交所需条件后确认事务成功。

这里的数据页写入与事务提交没有一个适用于所有数据库的固定先后顺序。关键是保证恢复所需的信息不会因数据页提前写入而丢失。检查点（Checkpoint）用于推进或记录恢复所需的状态，减少后续恢复的工作范围，具体行为由数据库实现决定。

SQLite 的 WAL 模式有不同的具体组织方式：修改后的页面可以先追加到独立的 WAL 文件中，提交通过相应记录建立边界；检查点再将适当的页面内容转移到主数据库文件。读取者根据相应快照判断可见页面。

![SQLite WAL 模式中提交、读取与检查点的职责](../assets/intro-sqlite-wal.svg)

不能认为只要使用 WAL 就一定不会丢失最近的事务。同步设置、底层系统对写入的保证及故障类型都会影响持久性。

## 实际验证一次数据库备份与恢复

下面使用 SQLite 支持的备份接口创建一致的数据库副本，再关闭连接并重新打开副本验证数据。实验只使用临时文件。

```python
import sqlite3
import tempfile
from pathlib import Path
from contextlib import closing

with tempfile.TemporaryDirectory() as directory:
    source = Path(directory) / "original.db"
    backup = Path(directory) / "backup.db"

    with closing(sqlite3.connect(source)) as db:
        with db:
            db.execute("CREATE TABLE registrations (name TEXT)")
            db.execute("INSERT INTO registrations VALUES ('小林')")
        with closing(sqlite3.connect(backup)) as copy:
            db.backup(copy)

    with closing(sqlite3.connect(backup)) as restored:
        assert restored.execute("SELECT name FROM registrations").fetchall() == [("小林",)]
        assert restored.execute("PRAGMA integrity_check").fetchone()[0] == "ok"
```

integrity_check 用于检查 SQLite 数据库内部结构的部分完整性条件，并不能证明业务数据正确或所有恢复要求都满足。因此还需要结合实际业务查询和恢复时间进行检查。

## 为什么备份是独立的问题

假设使用者误删除了全部报名记录，或者存储设备发生不可恢复的故障。

事务机制可能正确地完成了一次删除，却不会因为这次操作违背使用者的真实意图就自动恢复记录。

备份（Backup）是为了在需要时恢复数据而保留的独立副本或恢复材料。恢复（Restore）则是利用这些材料重建可用数据的过程。

复制数据库文件并不总能得到有效备份。正在运行的数据库可能包含多个相互关联的文件，复制时也可能正发生修改。应当使用相应数据库支持的备份方法。

## 怎样知道备份真正有用

假设每天凌晨备份一次。如果下午设备损坏，我们可能丢失凌晨以来发生的修改。

能够接受的最大数据损失时间范围称为恢复点目标（Recovery Point Objective，RPO）。能够接受的恢复耗时目标称为恢复时间目标（Recovery Time Objective，RTO）。

它们是业务设计目标，并不是设置完成后就一定能够达到的结果。实际能力需要通过恢复演练验证。

## 数据的生命周期也需要设计

报名活动结束之后，是否还需要长期保存所有姓名？哪些工作人员应该继续访问这些记录？

保存更多副本可以提高某些故障下的恢复能力，但也增加需要保护的数据范围。

因此，备份策略还需要考虑访问权限、保存期限、加密和删除规则。这些将在安全与隐私部分继续讨论。
