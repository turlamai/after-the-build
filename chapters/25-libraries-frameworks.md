# 为什么开发软件不需要每次从头开始

在学习图形界面时，我们使用了窗口和按钮的概念。假设每个开发者都要重新实现字体绘制、窗口管理、文本输入和事件处理，那么仅仅制作一个报名界面就需要投入大量工作。

已经有人实现的通用功能，可以由不同的程序重复使用。

## 库提供已经实现的能力

将可复用的软件功能组织起来供其他程序使用，通常称为库（Library）。

例如 Python 提供处理日期、读取文件和转换数据等功能的标准库（Standard Library）。开发者还可以使用第三方编写的库。

下面是一段使用标准库的例子：

```python
from datetime import date

deadline = date(2030, 6, 1)
today = date(2030, 5, 30)
print((deadline - today).days)
```

预期输出 2。

这段程序不需要自己实现月份长度、日期相减等规则，而是按照 datetime 模块提供的接口调用已有能力。

库能减少重复工作，但使用者仍要了解它对输入、输出及异常情况的规定。例如真实的报名截止时间还可能需要考虑时区，而不是只比较日期。

## 框架为什么不只是更大的库

当我们编写普通计算程序时，通常由自己的代码决定什么时候调用库函数。

但对于 GUI 应用，可能是界面工具启动事件循环，等待用户输入，再调用我们提供的报名处理函数。

这意味着软件不只是提供几个可调用功能，它还为应用建立了整体组织方式，并在适当时刻调用开发者实现的部分。

这类提供应用组织结构及运行规则的软件通常称为框架（Framework）。

库与框架之间并没有绝对清晰的产品分类。同一个工具可能同时提供可直接调用的库和负责组织应用运行的框架能力。我们需要理解的是控制流程由谁负责，而不是只看产品名称。

## 什么是依赖

如果报名应用需要某个图形库才能工作，那么这个库就是应用的一项依赖（Dependency）。

库自己也可能依赖其他库。一个看似简单的应用，最终可能需要多个软件组件才能正确构建和运行。

不同版本的库可能提供不同接口，甚至具有不兼容的行为。如果开发设备使用某个版本，而另一台设备安装的是不同版本，同一份源代码就可能表现不同。

这就是为什么工程师会记录依赖名称和版本要求。

## 为什么安装一个包可能引入多个包

假设应用依赖虚构的软件包 A，A 又依赖 B。即使应用没有直接调用 B，B 仍可能是运行 A 所需的依赖。这种关系称为传递依赖（Transitive Dependency）。

如果应用还使用 C，而 C 要求 B 的另一个不兼容版本，就可能出现依赖冲突。包管理器需要依据版本约束和生态规则寻找可用组合；不同生态对能否同时安装同名包的多个版本有不同规定。

![直接依赖、传递依赖与版本约束](../assets/intro-dependency-graph.svg)

隔离项目依赖也很重要。例如 Python 的虚拟环境（Virtual Environment）通常可以为一个项目提供独立的包安装位置，降低与其他项目互相影响的可能。它不是完整的操作系统安全沙箱，也不会自动阻止包访问用户文件。

依赖清单告诉我们项目要求什么，锁定文件记录选中了什么，实际安装环境则决定运行时能取得什么。三者需要互相核对。

## 怎样管理许多依赖

软件包（Package）是一种用于组织和分发软件组件的形式。不同语言及操作系统具有各自的软件包组织规则。

包管理器（Package Manager）负责查找、安装和管理符合其生态规则的软件包，并可能处理依赖关系。例如 Python 生态常见 pip，JavaScript 生态常见 npm。

项目可以通过依赖清单记录需要的组件及版本约束。一些生态还使用锁定文件（Lockfile）记录某次解析得到的具体依赖版本，以提高构建的可重复性。锁定文件也不能单独保证不同平台得到完全一致的行为。

安装第三方依赖可能执行外部代码，因此应当确认来源、必要性和可信程度。我们会在安全部分深入讨论这类问题。

选择一个库并不是选择越多功能越好。应该考虑它是否解决真实需求、接口是否稳定、目标平台是否受支持，以及维护成本如何。
