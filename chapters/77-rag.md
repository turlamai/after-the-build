# 怎样让模型根据自己的项目资料回答问题

假设我们要求模型说明报名系统目前采用什么数据库。模型训练时可能没有见过我们的项目，更不可能天然知道刚刚完成的修改。

即使它知道 SQLite 和 PostgreSQL 的原理，也不能仅凭这些知识判断当前项目采用了哪一种。

我们需要把实际项目的证据带入模型计算。

## 检索与生成可以组合起来

首先根据问题取得相关资料，例如配置文件、架构说明或最近的提交记录。

然后将相关内容与问题一起组织进模型输入，并要求回答以这些材料为依据。

这种将检索得到的信息用于辅助生成的方式，通常称为检索增强生成（Retrieval-Augmented Generation，RAG）。

![检索资料并将证据加入模型输入](../assets/intro-rag-pipeline.svg)

RAG 不要求每次重新训练模型。它主要改变本次推理能够利用的信息。

## 实际流程有哪些组成部分

对于一个项目文档系统，可以采用如下流程：

1. 读取允许访问的项目资料，并记录文件位置、版本及其他来源信息。
2. 将文档划分成合适片段，以便后续检索。
3. 根据需要建立关键词或向量索引。
4. 收到问题时检索相关片段，并选择适合加入上下文的材料。
5. 调用模型生成回答，并保留支持结论的证据位置。

划分片段的工作常称为分块（Chunking）。片段太短可能缺少背景；太长则可能引入大量无关内容。实际选择需要考虑文档结构及问题类型。

将向量检索与关键词检索组合是一种常见设计，但并不是 RAG 的必要定义。

## 一个有证据的问题应该怎样回答

假设某份虚构项目配置包含：

```text
database_driver = sqlite
database_path = data/registration.db
```

如果已经确认这份文件属于当前使用的目标环境，那么它可以作为判断该环境使用 SQLite 的证据。

但如果另一份生产配置使用不同数据库，就不能据此断言所有环境都使用 SQLite。

因此，资料来源、版本和适用范围与资料内容同样重要。

## 检索成功并不意味着答案正确

检索可能找错文档，模型也可能忽略材料或者产生材料没有支持的内容。

这种生成结果缺乏事实依据或与事实不符的现象，常被称为模型幻觉（Hallucination）。

改善方法包括增加准确检索、要求给出证据、验证关键结论，并在材料不足时明确说明不确定性。

还需要将检索内容作为数据处理，而不是让文档中任意文字自动成为可执行指令。对敏感资料的权限检查应在检索和使用过程中真正落实。

RAG 让模型能够利用外部知识，但它仍然主要在生成内容。若我们希望系统真正读取当前文件、运行测试或修改项目，还需要进一步引入工具调用。
