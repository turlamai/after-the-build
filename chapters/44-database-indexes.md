# 数据库为什么能够快速找到记录

假设报名表包含一百万条记录，而我们只想知道编号 5021 对应的姓名。

一种正确的查找方法是从第一条记录开始检查，直到找到目标。

但如果经常需要按照编号查找，我们就希望建立一种能够减少查找工作的辅助结构。

## 从有序数字理解查找

观察以下八个数字：

3、8、12、17、23、31、42、55。

如果我们希望找到 42，可以先检查中间附近的数字 17。由于 42 大于 17，可以排除左侧范围，再继续检查右侧的中间位置。

每一步利用顺序缩小可能范围。这种方法称为二分查找（Binary Search）。

在已经排序的数组上，二分查找所需比较次数大致随记录数的对数增长，而逐条扫描在最坏情况下需要与记录数成比例的比较次数。

这里先建立一种直觉：有组织的数据可以显著降低寻找目标所需的工作量。

## 索引保存额外的查找结构

数据库索引（Index）是为了支持某些访问方式而建立的辅助数据结构。

例如，我们经常按照 event_id 查询报名表，可以为这一列建立索引：

```sql
CREATE INDEX idx_registrations_event
ON registrations(event_id);
```

数据库可以利用适当的索引查找匹配活动的记录，而不一定从头扫描整张表。

实际数据库常使用 B 树家族等适于分层查找的结构，也可能提供其他类型的索引。二分查找的例子只是为了建立有序查找的基础，不表示数据库必然把全部记录保存在一个排序数组中。

## 为什么树形索引适合存储设备

已排序的数组适合二分查找，但插入新数据时可能需要移动大量元素。数据库还需要考虑：数据并不总能完整放在内存里，每次访问存储设备通常会读取一组字节，而不是只读取一个数字。

一种常见设计是把有序查找组织成多层节点。每个节点包含若干用于划分查找范围的键，并指向下一层相应节点。B 树及 B+ 树是这类设计中的重要结构。

以一棵虚构的 B+ 树为例，根节点使用 20 和 40 划分范围。查找键 35 时，沿着 20 至 39 对应的分支继续查找；最终在叶节点取得键及对应记录或定位信息。

![简化 B+ 树的范围划分与叶节点查找](../assets/intro-bplus-tree.svg)

B+ 树通常把完整的数据条目或记录定位信息组织在叶节点中，叶节点还常通过链接支持连续范围访问。实际数据库的节点格式、分隔键规则、记录保存位置及索引实现并不完全相同。

当节点可以容纳许多键时，树不必很高就能管理大量记录。插入或删除时，数据库可能需要分裂、调整或合并节点以维持结构。这也是索引会增加写入成本的原因之一。

## 一个索引不一定适合所有查询

假设为报名表建立联合索引 (event_id, id)，先按照活动编号排列，再按照报名编号排列。查询某项活动的报名者，并按照编号排序时，通常有机会利用这种排列。

但如果查询条件只有 id，就未必能够利用同一个索引高效定位。具体是否采用索引、是否还需排序以及如何访问表，由数据库优化器和实际条件决定。不要将简单的前缀规则理解为所有数据库都没有例外的保证。

## 为什么不为每一列都建立索引

索引本身需要存储空间。

插入、删除或者修改记录时，相关索引通常也需要维护。因此，索引可能减少某些读取操作的工作量，却增加写入及存储成本。

如果一次查询需要返回几乎整张表，扫描可能比通过某些索引逐条定位记录更合适。

数据库会根据可用信息选择执行策略。描述如何执行查询的方案通常称为查询执行计划（Query Execution Plan）。

## 观察而不是猜测

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE registrations (id INTEGER PRIMARY KEY, event_id INTEGER)")
db.execute("CREATE INDEX idx_event ON registrations(event_id)")
plan = db.execute(
    "EXPLAIN QUERY PLAN SELECT id FROM registrations WHERE event_id = ?",
    (1,)
).fetchall()
print(plan)
db.close()
```

这段实验展示 SQLite 提供的查询计划信息。具体文本可能随版本和查询条件而变化，因此不应把某个固定输出当作所有环境的正确答案。

性能优化需要根据实际数据规模、查询条件和测量结果选择，而不能只凭「索引越多越快」这样的说法。
