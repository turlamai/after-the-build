# 软件究竟在防止什么

如果我们说「报名网站必须安全」，这句话还不足以决定应该实现哪些机制。

有些问题来自错误配置，有些来自外部输入，有些来自权限过大的内部程序，也有些来自设备丢失。不同问题需要不同保护方式。

## 先确定需要保护的东西

报名系统中的姓名、活动名单、账户凭据和服务配置都可能是需要保护的资产（Asset）。

我们希望未经允许的人不能读取数据，希望记录不会被未授权地修改，也希望服务能够正常工作。

这对应信息安全中的三个常见目标：

- 保密性（Confidentiality）：信息不被未经授权地披露。
- 完整性（Integrity）：信息不被未经授权或非预期地修改。
- 可用性（Availability）：获授权使用者能够在规定条件下获得服务。

某项措施可能只保护其中一个目标。备份主要改善恢复能力，但未加保护的备份也可能造成信息泄露。

## 什么是威胁与信任边界

威胁（Threat）是可能损害资产的情况或行为；漏洞（Vulnerability）是可能被利用的弱点。风险则需要结合发生可能性、影响及具体条件评估。

我们可以先画出报名信息如何经过浏览器、后端和数据库，再标出每一处需要判断输入是否可信的位置。

信任边界（Trust Boundary）是系统中信任条件或控制权限发生变化的边界。例如，来自浏览器的请求进入后端时，后端不能直接把所有字段视为正确且已授权的数据。

![外部请求、后端及数据库之间的信任边界](../assets/intro-trust-boundaries.svg)

系统化分析需要保护的资产、可能发生的问题及对应措施，通常称为威胁建模（Threat Modeling）。

## 输入是数据，不应自动成为指令

第 43 章学习 SQL 时，我们使用参数占位符传递姓名等值。

如果程序将任意输入直接拼接进查询语句，数据库可能把输入的一部分解释成查询结构，而不是普通数据。这类问题称为 SQL 注入（SQL Injection）。

正确使用数据库提供的参数绑定接口，可以避免许多由数据与 SQL 语句混合造成的问题。动态表名等不能按普通值绑定的部分，需要使用适当的固定映射或其他安全构造方式。

相似的原则也适用于命令执行及网页显示：用户输入应根据其进入的具体环境进行验证、编码或安全构造。

## 为什么网页也需要区分数据与代码

显示报名者姓名时，应用应当把姓名作为文字，而不是把其中的特殊字符解释成网页结构或脚本指令。跨站脚本攻击（Cross-Site Scripting，XSS）涉及不可信内容被当作网页中的可执行代码处理。

应使用适合输出上下文的编码、安全的文本插入接口及成熟框架提供的保护机制。允许富文本时，还需按相应规则清理内容。内容安全策略（Content Security Policy，CSP）可以限制浏览器加载或执行部分资源，作为额外保护，但不能代替正确处理不可信内容。

下面的实验只比较普通文本与 HTML 转义结果：

```python
from html import escape
name = "A & B"
assert escape(name) == "A &amp; B"
```

HTML 转义适用于相应的 HTML 文本上下文，不是 SQL、JavaScript 或所有其他环境的通用安全处理方法。

## 权限应该与职责相匹配

报名后端可能需要读取及修改报名表，但并不必然需要创建数据库管理员账户。

只授予完成任务所需的权限，称为最小权限原则（Principle of Least Privilege）。

这样，即使程序存在缺陷，也可以降低某些错误或攻击造成的影响。最小权限并不能修复程序漏洞，因此仍需要输入验证、依赖维护和测试等措施。
