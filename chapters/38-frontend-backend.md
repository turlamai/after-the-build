# 前端、后端与 API 怎样组成一个应用

我们的报名页面已经有输入框和确认按钮，但它没有保存真实报名信息。

如果两个申请者分别打开页面，每个人都只在自己的浏览器里修改人数，那么两个人看到的结果可能不同，也无法可靠地执行总名额限制。

我们需要一个能够统一处理报名规则和数据的服务。

## 前端负责用户直接使用的部分

前端（Frontend）通常指承担用户交互及展示的应用部分。在常见 Web 应用中，前端代码由浏览器执行。

它可以读取用户填写的姓名，检查必要输入是否为空，显示剩余名额以及处理服务返回的结果。

前端检查有助于改善使用体验，但不能作为唯一的业务约束，因为客户端提供的请求可能绕过页面上的限制。

## 后端负责共同使用的业务处理

后端（Backend）通常指提供业务处理、共享数据访问等服务能力的应用部分。

对于报名应用，后端需要在收到请求后检查姓名、验证资格、判断剩余名额，并在合适条件下更新记录。

后端不一定负责所有网页显示工作。它可以生成网页，也可以主要提供供前端调用的数据接口。实际职责划分取决于应用结构。

## API 怎样把它们连接起来

第四部已经认识了 API：软件对外提供功能的接口与约定。在 Web 应用中，前端与后端可以通过 HTTP API 交换请求和结果。

我们可以定义一个简单的接口：

| 方法 | 路径 | 业务用途 |
|---|---|---|
| GET | /remaining | 获取剩余名额 |
| POST | /registrations | 提交报名 |

这只是示例接口，还需要约定请求体格式、身份要求、成功响应、错误情况及重复请求处理。

![浏览器与后端通过 HTTP 交换请求及响应](../assets/intro-web-architecture.svg)

设想前端点击确认后发送报名请求。后端取得申请信息，执行规则并返回结果。前端依据结果更新显示，而不是无条件地增加人数。

这才是多设备共享同一业务状态的基础。

## 为什么后端还需要更可靠的数据管理

假设两位申请者同时报名，而活动只剩一个名额。两个后端执行任务可能同时看到尚有名额，分别完成报名。

我们在进程和线程章节已经遇到共享状态的竞争问题。仅把判断放到后端，还不足以确保总人数不会超限。

下一部将学习结构化数据、数据库和事务，以解决这类问题。

## Web 并不等于互联网

互联网提供网络互联基础；Web 是建立在相应网络及协议之上的一种信息访问和应用体系。

电子邮件、其他实时通信服务以及许多设备控制协议，并不一定采用相同的网页运行方式。

理解这一层区别之后，我们可以回到序章的具体问题：为什么自己电脑上运行的网站，别人却无法访问？
