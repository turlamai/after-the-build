# 软件更新为什么不只是替换一个文件

报名软件已经被用户使用了一段时间。我们现在准备增加取消报名功能。

如果直接将新版程序覆盖旧版，是否就可以宣布更新完成？

## 软件会变化，用户的数据也会继续存在

源代码可以修改，构建产物可以重新生成。但用户原来保存的报名记录、偏好设置和其他信息，不应该因为更新程序而自动消失。

因此需要区别软件自身的文件、运行配置以及用户数据。它们可能采用不同的保存位置和生命周期。

更新过程中应尽量避免把需要长期保留的数据当成可以任意替换的构建产物。

## 如何识别不同版本

为了区分不同发布的软件，我们通常为版本分配明确标识，例如 1.0.0、1.1.0。

某些项目采用语义化版本（Semantic Versioning，SemVer），使用主版本号、次版本号和修订号表达公共 API 的兼容性变化。但并非所有版本号都遵循该规则，也不能仅凭编号保证更新行为正确。

版本标识需要与实际发布产物建立对应关系，否则用户报告某个错误时，我们很难知道应该检查哪一份程序。

## 自动更新需要完成哪些工作

一个典型的自动更新流程需要检查是否存在符合目标平台的新版本，取得相应产物，验证它的来源和完整性，在适当时刻安装，并确认更新后的应用能够继续运行。

如果更新失败，还需要能够保留或恢复可用版本。

这些工作不一定全部由应用自身承担。操作系统、应用商店或者独立的更新程序也可能参与。

## 怎样将更新设计成可以检查的过程

下载完成后，不应立即覆盖当前可用程序。常见做法是先把新版本准备到独立位置，验证下载完整性及预期发布者，再在适当时刻切换使用的版本。

切换后需要实际验证应用能否启动以及重要功能是否正常。如果验证失败，应按照事先设计的恢复策略处理，而不是不断重复同一安装操作。

更新过程中可能出现下载中断、磁盘空间不足、文件正在使用、权限不足或突然断电。更新设计应考虑这些失败状态，并记录当前实际启用的版本。

版本切换方式取决于平台及文件系统，不能假定所有文件替换都具有原子性。对于已经发生不兼容数据迁移的情况，也不能只依赖程序文件回退。

## 为什么回退旧程序有时不能解决问题

假设旧版报名软件只记录姓名，新版增加了报名时间，并改变了数据保存方式。

升级后，新版数据可能不再能被旧版正确读取。此时仅把可执行文件恢复成旧版，仍然不能保证系统可以工作。

把旧的数据表示转换成新表示的过程通常称为数据迁移（Data Migration）。更新设计需要考虑迁移是否可逆、如何备份、失败如何恢复以及旧版本是否仍能识别新数据。

## 从个人使用走向多人使用

到这里，我们已经理解了一个应用怎样处理事件、组织模块、利用软件库、生成产物并持续更新。

然而，我们的报名软件仍然主要运行在一台设备上。如果希望不同的人都能通过自己的电脑或手机报名，而且看到同一份最新名单，就必须让多台计算机交换信息。
