# 程序需要使用秘密，怎样才能不把秘密公开

报名后端可能需要使用数据库密码，云平台可能要求访问令牌，自动化流水线也可能需要具有发布权限的凭据。

如果直接将这些秘密写入公开源代码，其他人取得仓库后就可能获得相关权限。

## 配置与凭据的区别

监听端口、日志级别和数据库服务地址通常属于配置（Configuration）。数据库密码、私钥及访问令牌等则属于需要保护的秘密（Secret）。

它们都可能随运行环境变化，但保护要求不同。

我们可以让应用从运行环境读取某项配置，而不是在代码里固定写入生产秘密。例如：

```python
import os

port = int(os.environ.get("APP_PORT", "8080"))
assert 1 <= port <= 65535
print(port)
```

这段示例读取非秘密配置。环境变量能够帮助分离代码与配置，但并不自动提供秘密存储保护。

操作系统、进程管理工具、诊断输出及相关权限仍可能影响环境变量的可见范围。

## 秘密应当由适当机制提供

生产系统可以使用专门的秘密管理服务（Secret Manager）或平台提供的受保护凭据机制，依据运行身份及授权提供必要信息。

短期凭据在有效期结束后失效，可以减少某些长期泄露风险。但仍然需要限制作用范围、保护生成及分发过程。

不同环境应该使用不同凭据。开发人员在本地测试时不应默认拥有生产数据库的完整管理权限。

## 权限范围与运行身份

对于自动构建任务，可以分别授予读取源码、上传测试产物和发布正式版本的权限，而不是所有任务共用一个长期管理员令牌。

工作负载身份（Workload Identity）是让运行中的服务或任务通过受控机制证明自身身份的一类方案。它可以帮助平台按任务身份授予短期凭据，减少在代码和配置中长期保存秘密的需求。

短期凭据仍可能在有效期内被滥用。因此应限制权限范围、有效时间、可访问资源，并保留合适的审计记录。测试任务不应无条件取得生产发布凭据。

## 删除代码中的密码不等于解决泄露

假设一个数据库密码已经被提交到 Git 仓库。随后删除该行，只会改变新的提交内容；旧提交中可能仍然存在原始密码。

正确的处理应优先使已泄露的凭据失效，并在必要时生成新凭据。这可能涉及撤销（Revocation）或密钥轮换（Rotation）。

之后还需要调查泄露范围、检查使用记录、处理仓库历史及其他副本，并按照实际影响采取适当措施。不能保证通过修改 Git 历史就能收回所有已经被复制的数据。

## AI Agent 也应该受到权限限制

如果 Agent 只需要修改书籍内容，它不应同时获得生产数据库管理权限和发布系统全部控制能力。

把任务所需的权限与不必要权限分开，可以限制错误操作的影响。高影响操作还应具有明确的授权和可核查的记录。

秘密也不应该被复制进普通提示词、公开问题记录或无保护日志。
