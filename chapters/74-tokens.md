# 模型读取的不是直接可理解的文字

第一部已经讲过字符与 UTF-8 编码的关系。现在我们知道，字符串进入程序时，可以被表示为字节。

语言模型还需要一种适合自身计算的序列表示。

## 怎样将文字变成可处理的序列

语言模型的分词器（Tokenizer）根据规定的算法和词汇表，将输入转换成一系列单位，称为 Token。

Token 可以对应一个单词、单词的一部分、若干字符、标点或其他编码单位，具体取决于分词器设计。

例如，为了说明机制，我们可以虚构一个小型词汇表：

| Token 表示 | 编号 |
|---|---:|
| 活动 | 10 |
| 报名 | 11 |
| 成功 | 12 |

如果该教学分词规则将「活动报名成功」分成上述三个单位，模型输入序列就可以是 10、11、12。

这个词汇表完全是教学假设，不是任何实际商业模型的 Token 编号或分词结果。

## 编号还不能直接表示含义

编号 10 和 11 相邻，并不意味着这两个 Token 的含义一定相似。

模型可以通过一组数值表示与 Token 相关的信息。通常，Token 的编号用于取得对应的向量表示，然后模型使用这些数值进行后续计算。

向量（Vector）可以先理解成按照顺序组织的一组数，例如 [0.2, -0.5, 0.8]。我们会在第 76 章进一步解释它怎样用于表示和检索数据。

## 输出怎样逐步形成

许多生成式语言模型根据当前已有的 Token 序列计算下一 Token 的概率分布。随后，生成过程根据相应选择规则确定一个 Token，将它加入序列，并继续下一次计算。

例如，在虚构的教学分布中：

| 候选 Token | 概率 |
|---|---:|
| 成功 | 0.7 |
| 失败 | 0.2 |
| 结束 | 0.1 |

这不是实际模型输出，只用于说明概率分布和选择规则是不同的事物。

模型可以采用不同生成策略，因此相同输入不一定每次产生完全相同的文字。

选择了概率较高的输出，也不代表输出一定符合客观事实。概率描述的是模型在相应条件下的计算结果，不是对现实世界真实性的直接验证。

## Token 为什么会影响成本

模型处理的序列长度影响计算及资源需求。服务提供者也可能根据输入、输出等 Token 使用量计费。

汉字数量、英文单词数量、字节数量和 Token 数量之间没有一个适用于所有模型的固定换算关系。实际计算应使用对应模型的分词规则或服务返回的使用量。
