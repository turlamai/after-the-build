# 第 18 章 版本控制、依赖管理与可复现构建

> 每一次软件变更都应能够定位、审查、验证并在适当条件下恢复。

## 一、Git 的基本模型

版本控制（Version Control）记录文件变更及其历史。Git 是分布式版本控制系统；GitHub 是提供 Git 仓库托管及协作功能的平台，二者不能混为一谈。

Git 提交（Commit）记录所跟踪文件的快照、父提交和相关元数据。Git 可以复用相同对象，并在存储层采用压缩等方式节省空间，但不能简单描述为每次只保存差异。

工作区（Working Tree）包含当前文件，暂存区（Staging Area 或 Index）记录准备提交的内容，本地仓库（Repository）保存提交及其他 Git 对象。远程仓库（Remote Repository）是用于交换提交的另一仓库。

## 二、分支与协作

分支（Branch）是指向提交的可移动引用。开发者在独立分支上完成工作后，可以通过合并（Merge）整合历史。变基（Rebase）则通常将提交重新应用到新的基点上，产生新的提交标识。

Pull Request（PR）是在托管平台发起的变更审查请求，不是 Git 本身的基础对象。它通常结合差异审查、CI 检查和讨论，帮助团队确认变更可接受。

常用只读命令如下：

| 命令 | 用途 |
|---|---|
| git status | 检查当前工作区与暂存状态 |
| git diff | 查看尚未暂存的差异 |
| git diff --staged | 查看暂存差异 |
| git log --oneline | 查看提交历史 |
| git show HEAD | 查看当前提交内容 |

提交不会自动推送到远程。push 用于推送引用及对象，fetch 获取远程更新，pull 通常获取并整合远程变更。

## 三、恢复与变更控制

git revert 通过新增提交撤销指定提交的影响，适合在共享历史中保留变更记录。git restore 用于恢复工作区或暂存区文件，可能丢弃未提交修改；git reset 可以改变分支及相关状态，其中某些模式会丢失工作区变更。

不能保证所有文件和状态都能通过 Git 找回。未跟踪文件、未提交内容、外部数据库及未推送提交可能不在远程仓库中。强制推送会重写共享引用，应受严格控制。

## 四、软件版本与依赖

语义化版本（Semantic Versioning，SemVer）约定 MAJOR.MINOR.PATCH 分别用于不兼容 API 变更、向后兼容功能添加及向后兼容修复，具体项目未必完全遵守。

依赖清单（Dependency Manifest）表达项目需要的包和版本约束；锁定文件（Lockfile）记录解析后的具体依赖版本等信息。直接依赖由项目声明，传递依赖由其他依赖引入。

依赖范围可能导致重新解析时选择不同版本。锁定文件、运行时版本、构建工具链和环境配置有助于可复现构建（Reproducible Build），但不足以保证字节级完全一致。

软件物料清单（Software Bill of Materials，SBOM）记录软件组件及版本信息，用于依赖追踪和供应链管理。升级依赖应检查兼容性、安全公告、许可证及测试结果。

## 五、实践：在临时仓库观察提交

确认安装 Git，在新建且独立的测试目录中初始化仓库。创建一个 README.md，运行 git status 查看未跟踪文件，再用 git add README.md 暂存并运行 git diff --staged。配置好练习身份后执行 git commit -m "Add initial README"。

修改 README 内容，运行 git diff，观察提交前后的差异。不要在现有项目中执行破坏性恢复命令作为练习。可以进一步提交修改，在临时仓库通过 git revert HEAD 观察新增撤销提交的行为。

## 六、与 Agent 协作

请先检查当前分支、工作区状态、基准提交及已有变更，保留用户未提交内容。在独立分支完成最小范围修改，执行测试和构建，提供可审查的提交差异。更新依赖时解释版本选择及锁定文件变化。未经授权不强制推送、不重写共享历史、不合并未验证 PR。
