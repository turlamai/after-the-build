# 为什么每次提交都应该自动检查

开发者完成一次修改，并在自己的电脑上运行了测试。但其他开发者、服务器和最终用户不一定拥有相同的运行环境。

我们需要一种可重复的方法，从确定的代码版本开始，自动执行必要的构建和测试步骤。

## 把检查流程写成规则

持续集成（Continuous Integration，CI）是一种经常整合代码变化、并通过自动化检查及时发现问题的开发实践。

在 GitHub 等平台上，可以配置某些事件发生后启动自动化工作，例如创建 PR 或推送提交。

执行环境通常称为运行器（Runner）。它按照配置取得代码、安装所需依赖、执行命令并记录结果。

![从提交到自动化构建和测试](../assets/intro-ci-pipeline.svg)

将一组具有依赖及执行顺序的任务组织起来，可以形成流水线（Pipeline）。流水线不一定每个任务都顺序执行：彼此独立的检查也可以同时运行。

## 一份简化的工作流

以下是 GitHub Actions 工作流的教学片段。它假设仓库已经包含使用标准库 unittest 组织的 Python 测试。将其保存到 .github/workflows/test.yml 才构成相应平台可以识别的配置文件。

```yaml
name: Tests
on:
  push:
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m unittest discover
```

该配置描述的是平台如何取得代码、准备 Python 并运行测试。示例使用的是教学版本选择，不是关于当前最新组件版本的声明；正式项目需要审核外部组件的版本和权限，并确认测试确实被发现和执行。仅仅退出码为 0，不能证明存在有效测试。

## 构建产物应该对应可追踪的代码

第四部已经区分源代码和构建产物。CI 可以在明确的提交版本上生成产物，并记录构建环境和相关结果。

如果正式发布时又从一份无法确认的本地代码重新打包，就可能无法确定实际交付物是否与经过测试的代码一致。

因此，最好能够追踪产物来自哪个提交、使用哪些依赖及哪些构建配置。对于要求较高的项目，还需检查构建可重复性及供应链安全。

## 自动化不能代替审查

代码审查（Code Review）用于检查变更是否符合需求、设计约束和维护要求。自动测试可以提供重要证据，但不能完整判断一项设计是否适合业务。

使用 AI 开发也应遵循同样原则。一个自动生成的 PR 应包含真实变更、测试证据和已知限制，而不是仅凭模型对自己的代码进行评价。
