第三部 · 安全与工程判断

第 21 章 隐私工程：数据流、追踪与授权

隐私保护要求明确数据的收集目的、处理范围、访问主体和生命周期。

一、个人数据与处理目的

个人数据（Personal Data）通常指与已识别或可识别自然人相关的信息，具体法律定义因司法辖区而异。姓名、邮箱、设备标识、位置以及能够关联到个人的活动记录都可能属于个人数据。

数据最小化（Data Minimization）要求按照处理目的限制所收集和保留的数据。一个活动报名系统可能需要联系方式，但不一定需要身份证号码、精确位置或通讯录。

隐私工程（Privacy Engineering）不仅关注数据是否泄露，也关注数据是否被超出预期目的使用、保留过久或传给不必要的第三方。

二、Cookie 与浏览器存储

HTTP Cookie 是服务器通过 Set-Cookie 响应头等机制交给浏览器保存的状态数据。浏览器根据域、路径、有效期及其他规则决定何时发送 Cookie。

Secure 属性限制 Cookie 在安全连接中发送，HttpOnly 限制客户端脚本直接读取 Cookie，SameSite 影响跨站请求中 Cookie 的发送条件。这些属性作用不同，并不能代替服务端授权或完整的 CSRF 防护。

Local Storage 与 IndexedDB 是浏览器提供的其他存储机制，通常不会像 Cookie 那样自动随 HTTP 请求发送。若数据只存在浏览器中，清理站点数据可能造成数据丢失。

三、第三方请求与追踪

网页加载第三方脚本、分析组件、广告资源或字体时，浏览器可能向相应服务发起网络请求。请求及脚本可获得的数据范围取决于浏览器安全模型、权限、实现和配置。

第三方 Cookie、设备指纹（Fingerprinting）、账户关联和服务端事件上报均可能用于跨场景关联活动。设备指纹通常利用多种环境属性生成识别信号，其准确性并非绝对。

看到与近期话题相关的推荐并不能直接证明设备在窃听，也不能据此排除所有其他数据收集行为。需要检查应用权限、实际网络活动和相关服务的处理说明。

四、OAuth 与 OpenID Connect

OAuth 2.0 是授权框架，允许客户端在一定范围内访问受保护资源。OpenID Connect（OIDC）是在 OAuth 2.0 之上构建的身份层，常用于登录场景。

授权范围（Scope）约束客户端获得的能力。访问令牌用于访问受保护资源；OIDC 的 ID Token 则包含有关认证事件及用户身份的声明。两者用途不同，不应随意互换。

撤销授权可以限制后续访问，但第三方此前获得的数据未必自动删除。应用还应提供适当的账户管理和数据删除流程。

五、数据生命周期与 AI 服务

数据生命周期包括收集、传输、存储、使用、共享、归档和删除。每一阶段都应明确处理目的、责任主体、访问权限及保留期限。

匿名化（Anonymization）旨在使个人无法被合理重新识别；假名化（Pseudonymization）通过替换标识降低直接识别风险，但仍可能通过附加信息重新关联。仅删除姓名并不保证匿名化。

使用 AI API、检索服务或 Agent 时，应确认输入、日志、工具结果和向量索引是否包含个人数据，并查阅具体服务的数据处理、保留和训练政策。不能仅凭本地或云端的名称判断隐私保证。

六、实践：审查数据流

打开自己控制的测试站点，使用浏览器开发者工具查看 Network 与存储面板。记录请求目的域名、Cookie 属性和本地存储类型。区分必要的业务请求与第三方服务请求。

建立数据清单，逐项记录字段、目的、保存位置、访问主体、第三方接收方、保留期限及删除方式。不要将真实会话 Cookie 或用户标识复制到公开文档。

七、与 Agent 协作

请从项目源码、测试配置和网络请求中整理数据流，识别不必要的收集字段、第三方 SDK、日志中的个人数据及权限范围。设计数据导出、删除和保留机制，并在虚构账户中验证。对法律义务不确定之处明确标注，交由适当专业人员确认。

八、知识检验

  • Cookie 与 Local Storage 有何区别？
  • OAuth 2.0 与 OIDC 各自解决什么问题？
  • 撤销第三方授权为何不等于删除历史数据？
  • 假名化为何不必然构成匿名化？

进阶方向：隐私影响评估、数据分类、差分隐私、浏览器安全模型、OAuth 2.0 Security Best Current Practice。参考 RFC 6749、RFC 9700 与 OpenID Connect Core。
