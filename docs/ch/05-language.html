第一部 · 计算机技术基础

第 5 章 编程语言、构建与运行时

即使由 AI 编写代码，也需要理解代码怎样变成运行中的软件。

一、源代码与语言

源代码（Source Code）使用编程语言表达算法、数据和控制逻辑。语法（Syntax）规定合法表达形式，语义（Semantics）规定表达的行为。语法正确并不意味着业务逻辑正确。

变量（Variable）关联程序中的值或存储位置，数据类型（Data Type）规定值的表示和允许的操作。函数（Function）封装可调用的逻辑，参数传入信息，返回值提供结果。条件与循环决定控制流。

例如：

def total(price, quantity):
    return price * quantity

print(total(20, 3))

函数 total 接收两个参数并返回乘积，程序输出 60。它并没有验证数量是否为负数，也没有处理货币精度；这些属于需求及实现约束。

二、编译器、解释器与运行时

编译器（Compiler）将程序转换为另一种表示，例如机器代码或字节码。解释器（Interpreter）按照程序表示执行其行为。即时编译（Just-in-time Compilation，JIT）可以在运行过程中生成机器代码。

运行时（Runtime）提供程序执行所需的环境和支持功能，例如内存管理、异常处理或标准库。Python、Java、JavaScript 等实现可能结合编译、解释和 JIT，不能简单按语言划分为互斥类别。

本机可执行程序也可能依赖动态链接库及操作系统接口。因此，成功编译与在目标系统成功运行是不同的验收条件。

三、模块、库与框架

模块（Module）组织相关代码；库（Library）提供可复用功能；框架（Framework）通常定义应用的组织方式和执行流程。API 规定组件之间可使用的接口。

依赖（Dependency）是软件所需的外部组件。包管理器（Package Manager）负责解析、安装和管理软件包。例如 npm、pip 等工具属于不同生态。依赖清单与锁定文件的职责不同，具体机制取决于工具。

安装依赖可能执行第三方代码，需要检查来源与权限。不要把自动安装成功等同于供应链安全。

四、构建与测试

构建可能包含编译、链接、资源转换及打包。构建产物（Build Artifact）是流程生成的文件。测试（Test）用于验证行为是否符合预期，不能由构建成功替代。

静态类型检查、Lint、单元测试、集成测试各自覆盖不同问题。静态检查可能发现不合法的类型或代码模式，但无法证明所有业务行为正确。

五、实践：理解代码行为

如果已安装 Python 3，将前面的例子保存为 example.py，在测试目录中运行 python example.py（部分系统使用 python3）。将 quantity 改为 -3，观察结果。程序仍然可以合法执行，但它是否应该接受负数量需要业务规则决定。

请尝试用文字写出约束：数量必须为非负整数，非法输入应产生明确错误。再让 Agent 添加实现及测试，检查正常值、零、负数与非整数输入。

六、技术选型与 Agent

语言选择应根据目标平台、团队经验、生态、性能、部署和维护约束判断。不要单纯依据语言热门程度，也不要让 Agent 随意更换项目技术栈。

请 Agent 先识别现有语言、运行时版本、依赖清单、构建与测试入口；在保持接口兼容的前提下实现需求，提供代码差异及实际验证结果。未经授权不进行跨语言重写或大规模依赖升级。

七、知识检验

  • 语法正确为什么不能证明业务逻辑正确？
  • 编译器与运行时承担什么职责？
  • 库、框架和 API 有何联系？
  • 构建成功之后为什么仍需要目标平台测试？

进阶方向：链接器、ABI、类型系统、垃圾回收、异常处理与依赖解析。
