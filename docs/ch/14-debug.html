第二部 · 工程实践

第 14 章 软件质量：测试、调试与可观测性

修复的依据是证据，验收的依据是事先确定的可观察结果。

一、缺陷与故障

缺陷（Defect 或 Bug）是设计或实现中偏离要求的问题；故障（Failure）是系统运行时未能提供预期行为的表现。同一故障可能由不同缺陷或环境条件触发。

例如点击提交后没有提示，可能是前端事件处理错误、网络请求失败、后端异常，也可能是请求成功但页面没有刷新。只有现象不足以确定根因。

调试（Debugging）是发现、定位及修正问题的过程；测试（Testing）是通过受控输入和观察结果来检验系统行为。测试发现问题，调试寻找原因，两者不能互相替代。

二、如何复现与定位

复现（Reproduction）需要记录版本、运行环境、初始状态、输入和操作步骤，以及预期与实际结果。间歇性故障不能稳定复现时，也可以利用历史日志、故障转储和统计规律分析。

定位时先缩小故障范围，再建立可以被证据否定的假设。例如怀疑提交 API 失败，可以在浏览器 Network 面板检查请求是否发出、响应状态与耗时。如果没有请求，应优先检查前端；如果响应 500，应结合后端日志分析。

错误堆栈（Stack Trace）描述异常发生时的调用路径。异常类型、错误消息、文件位置和调用关系都有价值，但栈顶未必就是根因。日志应保留相关上下文并移除秘密及个人信息。

三、测试分层与回归

测试类型 验证对象 示例
单元测试（Unit Test） 独立函数或模块 金额计算
集成测试（Integration Test） 多组件协作 API 写入测试数据库
端到端测试（End-to-End Test） 用户完整流程 登录、报名、查看结果
回归测试（Regression Test） 修改后仍应满足的行为 修复报名后确认导出正常

边界值测试（Boundary Value Testing）关注最小值、最大值及边界附近输入；负向测试（Negative Testing）验证非法输入和未经授权的操作能否被拒绝。

一个测试通过只证明特定环境下被检查的行为符合断言（Assertion）。代码覆盖率（Code Coverage）可以帮助发现未测试路径，但高覆盖率不等于测试有效。

四、日志、指标与追踪

可观测性（Observability）关注如何通过系统输出理解内部状态。常见信号包括日志（Logs）、指标（Metrics）和追踪（Traces）。

日志记录事件，指标描述随时间变化的数值，例如请求数、延迟和错误率；分布式追踪通过 Trace ID 等标识关联一次请求跨服务的执行路径。监控（Monitoring）利用这些数据识别异常并触发告警。

生产环境发生故障时，应先减少影响、保全证据，再寻找原因。不要为了验证猜测随意清空数据、重启所有服务或关闭安全检查。

五、实践：设计一个报名接口测试

在独立测试环境准备一个虚构活动和测试用户，约定正常提交返回 201、重复提交返回 409。这里的状态码是本练习的接口契约，而非所有报名系统的必然设计。

执行首次报名、重复报名、非法输入、未授权访问及并发提交。检查 HTTP 响应和数据库记录数量。若修改了重复报名逻辑，再执行原有正常流程和导出功能，防止回归。

记录每个用例的实际结果。没有执行的用例标记为未验证，不能凭代码阅读填写通过。

六、与 Agent 协作

请先读取当前版本和故障日志，建立最小复现或说明无法复现的原因。对候选根因逐一检查证据；修复后增加能够覆盖原缺陷的回归测试，执行相关测试并报告实际退出码、失败用例和未验证范围。不要仅以刷新页面或清除浏览器数据作为修复依据。

七、知识检验

  • 缺陷和故障有什么区别？
  • 为什么 500 状态码不足以确定根因？
  • 单元测试通过为什么不能证明整个系统可用？
  • 日志、指标与追踪分别提供什么信息？

进阶方向：断点调试、故障注入、属性测试、模糊测试、OpenTelemetry、根因分析与事故复盘。
