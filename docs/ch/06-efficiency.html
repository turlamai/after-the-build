第一部 · 计算机技术基础

第 6 章 性能与算法：复杂度、瓶颈和测量

优化的依据是可复现的性能数据，而不是对代码速度的直觉。

一、性能指标

延迟（Latency）表示一次操作从开始到完成所需的时间；吞吐量（Throughput）表示单位时间内完成的工作量。并发数（Concurrency）表示同时进行的任务数量，不等于物理并行执行数量。

例如一个 API 平均响应时间为 100 ms，并不意味着每次都在 100 ms 内返回。P95 延迟为 300 ms 表示约 95% 的观测值不超过 300 ms。平均值可能掩盖少量极慢的请求，因此服务性能常同时观察吞吐量、P50、P95、P99 和错误率。

二、算法复杂度

算法（Algorithm）是解决问题的一组明确步骤。时间复杂度（Time Complexity）描述输入规模增大时操作成本的增长趋势。大 O 记号（Big O Notation）给出渐近增长上界，不直接表示秒数。

复杂度 典型操作 n 增加十倍时的代表性增长
O(1) 按数组下标读取 约不变
O(log n) 有序数组二分查找 增加少量步骤
O(n) 遍历全部记录 约十倍
O(n log n) 典型归并排序 超过十倍
O(n²) 比较所有记录对 约百倍
O(2^n) 枚举所有子集 远超过百倍

O(n²) 是平方级复杂度，不是指数级复杂度。真实时间还取决于常数开销、数据分布、缓存和 I/O。

例如查找名单中重复的用户，可以逐对比较，也可以将已出现的用户标识保存在哈希集合（Hash Set）中。后者在常见哈希实现的平均条件下可将时间复杂度从 O(n²) 降至 O(n)，但需要额外空间。最坏情况仍依赖实现和输入。

三、数据库索引与缓存

索引（Index）是支持查询的数据结构。数据库常使用 B-tree 等结构组织索引，从而减少扫描范围。索引也消耗存储空间并增加写入维护成本，不能保证每个查询都更快。

缓存（Cache）保存可以复用的结果，减少重复计算或远程请求。需要定义缓存键、过期时间和失效策略；否则可能返回过期数据。索引改变查询路径，缓存减少实际查询，两者解决的问题不同。

四、定位瓶颈

性能分析（Profiling）通过测量 CPU 时间、内存分配、I/O 或调用路径发现高成本区域。基准测试（Benchmark）在受控条件下比较实现；负载测试（Load Test）模拟不同请求规模和并发水平。

一次页面加载可能同时受数据库查询、网络往返、后端处理和浏览器渲染影响。数据库的 N+1 查询问题是典型例子：获取一组记录后又为每条记录单独发起查询，导致远程访问次数随记录量增加。仅优化本地循环无法解决这类问题。

五、实践：测量而不是猜测

在测试环境准备 100、1000、10000 条结构一致的虚构记录。对同一查询分别测量至少数次，记录数据规模、运行环境、是否预热、响应时间和结果正确性。

如果安装了 Python 3，可使用 timeit 模块测量简单查找：

python -m timeit -s "a=list(range(10000))" "9999 in a"
python -m timeit -s "a=set(range(10000))" "9999 in a"

部分系统使用 python3。这里构造容器的成本被排除在计时之外，因此结果只比较查找，不代表完整业务总耗时。将规模增加后重复实验。

六、与 Agent 协作

请在相同硬件、数据集和并发条件下建立性能基线，使用 profiler 或查询执行计划定位瓶颈。比较优化前后的延迟分位数、吞吐量、错误率和资源消耗，确保输出一致。不要为了性能删除必要的权限检查或数据校验。

七、知识检验

  • 延迟与吞吐量为何可能同时变化？
  • O(n²) 与 O(2^n) 有什么区别？
  • 索引为何可能降低写入性能？
  • 为什么只测一次平均响应时间不足以验收优化？

进阶方向：摊还复杂度、查询执行计划、缓存失效、Amdahl 定律、分布式链路追踪。
