第三部 · 安全与工程判断

第 22 章 工程决策：风险评估、技术选型与专业协作

技术可行性、工程可控性和组织责任是不同问题。能够生成软件，不等于具备交付高风险系统的全部条件。

一、从原型到正式系统

原型（Prototype）用于验证想法或技术可行性，最小可行产品（Minimum Viable Product，MVP）用于检验核心用户价值，生产系统则需要满足明确的质量、运行和责任要求。

一个能够录入客户资料的原型，并不自动具备权限隔离、数据保留、审计、备份和故障恢复能力。判断是否可以投入生产，应依据用途及验收标准，而不是界面完成度。

二、风险评估

风险评估（Risk Assessment）通常综合事件发生可能性、影响及不确定性。可以用低、中、高等等级构造风险矩阵，但这并不意味着能够精确计算所有事故的概率。

维度 需要回答的问题
数据与隐私 是否涉及敏感数据、他人数据或秘密？
业务影响 故障会影响哪些人和流程？
安全与合规 是否存在特定行业或法律要求？
可恢复性 是否有经过验证的恢复方案？
能力与资源 是否具备足够的测试、维护和专业审查能力？

医疗、金融交易、安全关键控制等高影响场景需要相应的专业工程流程和领域审查，不能仅凭 Agent 生成的代码及通用测试判断可用性。

三、技术选型与架构决策

技术选型（Technology Selection）是在约束条件下比较方案。除了初始开发效率，还应考虑兼容性、维护成本、供应链、团队能力、扩展性和退出成本。

架构决策记录（Architecture Decision Record，ADR）是一种记录重要决策及其背景、候选方案、理由和后果的文档。记录决策可以防止后续开发在缺少上下文时重复争论或无理由更换技术栈。

例如选择静态站点而非完整后端框架，可以记录：内容无需用户登录及数据库写入，静态部署满足要求，若未来引入个人账户则重新评估。这里的结论来自需求，而不是技术等级高低。

四、如何与专业人员协作

需求规格、接口契约、验收标准和风险清单是工程协作的共同输入。求助时应提供问题范围、版本、环境、复现步骤、已尝试操作及必要的脱敏证据。

协作方式可以是技术咨询、代码审查、安全评估、独立测试或完整外包。选择依据是缺失的能力及责任边界，不是简单地将所有问题交给同一个人。

对于第三方交付，应明确源代码、部署产物、配置、依赖许可、文档、测试结果、账号控制权和维护责任。知识产权归属及许可权利需要结合实际协议确认，不能仅根据源代码是否交付推断。

五、实践：编写架构决策记录

为一个虚构的活动报名系统编写 ADR，比较静态表单加托管后端与自建后端两种方案。明确用户数量、数据敏感度、可用性、预算、维护能力及迁移要求。

记录选定方案、未选择方案的理由和重新评估条件，再让 Agent 提出反例及遗漏风险。检查它的建议是否有依据，而不是只看结论是否符合偏好。

六、与 Agent 协作

请根据现有需求生成候选方案及决策矩阵，列出关键假设、依赖、风险、成本和验收证据。区分可以通过测试验证的技术问题与需要领域专家、法律或组织负责人确认的问题。不自行变更既定架构或扩大项目范围。

七、知识检验

  • 原型、MVP 与生产系统的验收重点有何区别？
  • 为什么风险不能仅用开发难度衡量？
  • ADR 应记录哪些信息？
  • 为什么代码交付不自动等于拥有全部知识产权？

进阶方向：需求工程、架构评审、FMEA、质量属性场景、许可证管理和技术尽职调查。
