第五部 · 网络与 Web

HTTP 究竟规定了什么

我们已经理解了地址、端口和数据传输。假设客户端通过网络连接报名服务，并发送以下文字：我想知道当前还有多少名额。

但是服务端不一定知道怎样解释这句话。客户端与服务端还需要共同规定操作的表达方式。

超文本传输协议（Hypertext Transfer Protocol，HTTP）为 Web 通信提供了请求与响应的通用语义。

一次 HTTP 请求是什么样子

为了理解消息结构，我们先看 HTTP/1.1 的文本形式：

GET /remaining HTTP/1.1
Host: registration.example.com

第一行指定请求方法、目标及协议版本。GET 通常用于获取资源的表示，/remaining 是这里约定的请求路径。

Host 是请求头字段，在 HTTP/1.1 中用于提供目标主机相关信息。空行表示这一部分消息头结束。实际 HTTP/1.1 传输使用规定的行结束符。

服务端收到请求后，可以根据方法和路径选择相应业务处理规则。

响应不只是业务数据

一种可能的响应是：

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 1

3

这里示例的响应体只有一个字节，即字符 3，不包含额外换行。

200 是 HTTP 状态码（Status Code），表示请求按照相应 HTTP 语义成功处理。Content-Type 描述返回内容的媒体类型及这里使用的字符编码，Content-Length 表示本例消息体的字节数。

响应体中的 3 是报名业务提供的数据。

方法、路径和业务规则

GET 可以用来读取剩余名额，POST 可以用于向服务提交报名信息。具体怎样使用路径、输入内容和响应结果，需要服务的 API 作出规定。

并不是所有 HTTP 请求都具有消息体，也不是所有响应都必须返回内容。

状态码有不同类别，例如 404 表示未找到相应资源，500 表示服务器遇到无法正常完成请求的内部情况。具体含义应结合 HTTP 规定和服务接口理解。

即使收到 200，也不应仅凭状态码就认定业务数据库已经按预期保存记录，还需要检查业务契约和实际结果。

消息体的长度为什么必须准确

考虑一个仅用于教学的 HTTP/1.1 请求。以下代码块为便于阅读使用普通文本换行；实际 HTTP/1.1 报文行使用 CRLF，头部与消息体之间有空行。

POST /api/registrations HTTP/1.1
Host: localhost:8000
Content-Type: application/json
Content-Length: 15

{"name": "Lin"}

最后一行采用 JSON 格式（一种用文本组织字段和值的约定，第 41 章将详细介绍），其中冒号之后包含一个空格。整行包含 15 个 ASCII 字节（不包含展示时附加的换行）。Content-Length 表示消息体的字节长度，不是字符数量。

对于非 ASCII 文字，需要先按照约定编码成字节再计算长度，例如中文姓名使用 UTF-8 后可能占用更多字节。

HTTP/1.1 也可以采用其他合法的消息定界方式。接收程序需要正确处理消息边界，不能假定一次 TCP 读取正好返回一条请求。

还要区分 HTTP 状态与业务状态。例如返回 201 通常表示资源已创建，409 可以表示业务状态冲突，但具体业务规则仍由 API 契约规定。客户端不能因为连接成功就直接显示报名成功。

URL 怎样指定访问目标

统一资源定位符（Uniform Resource Locator，URL）可以描述如何定位某项资源。

例如 http://registration.example.com:8080/remaining，其中 http 是方案，registration.example.com 是主机名，8080 是显式端口，/remaining 是路径。

HTTP 默认端口通常是 80，HTTPS 默认端口通常是 443；显式端口可以指定其他值。

HTTP/2 和 HTTP/3 不使用上面相同的文本报文编码，但仍保留相关 HTTP 请求和响应语义。HTTP/3 使用建立于 UDP 之上的 QUIC 传输协议。

普通 HTTP 不提供 HTTPS 所使用的加密及身份验证保护。我们在安全部分学习密码学基础后，会完整解释 TLS 与 HTTPS。现在的例子仅用于理解消息，不应通过未保护的公网 HTTP 提交真实个人信息。
