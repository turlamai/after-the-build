第九部 · 安全与隐私

HTTPS 怎样保护浏览器与服务器之间的通信

第五部介绍过 HTTP 请求及响应。如果通过普通 HTTP 提交报名信息，传输路径上的相关观察者可能看到消息内容，某些能够修改通信的参与者也可能改变消息。

HTTPS 在 HTTP 通信中使用传输层安全协议（Transport Layer Security，TLS）提供保护。这里以常见 TLS 1.3 的服务器证书认证及临时密钥协商握手为例建立模型。

第一步：找到连接目标

浏览器先根据 URL 确定访问目标，并使用适当的地址解析及网络传输机制建立通信。

DNS 返回正确地址并不单独证明对方身份。后续 TLS 握手还需要验证相应身份。

第二步：交换建立密钥所需的信息

客户端发送 ClientHello，其中包含支持的协议参数以及在典型握手中使用的密钥共享信息。

服务端通过 ServerHello 等消息确定相应参数，并提供自己的密钥共享信息。双方利用密钥协商与密钥派生机制建立握手及后续通信所需的密钥。

这里并不是服务器直接把最终对称密钥明文发送给浏览器。

第三步：验证服务器身份与握手

在使用服务器证书认证的典型完整握手中，服务器提供证书链，并使用与证书公钥对应的私钥生成相应握手签名。

浏览器按照信任配置检查证书链、目标域名及其他适用验证条件，并验证握手签名。TLS 还使用 Finished 等消息验证握手过程及相关密钥的正确性。

如果验证失败，不应把忽略证书错误当作正常修复方法。

实际协议的消息保护阶段和密钥派生过程更为精细；图中只展示理解依赖关系所需的主要步骤，不包含会话恢复、客户端证书认证及所有扩展。

握手阶段为什么已经有一部分消息受到加密保护

在典型 TLS 1.3 完整握手中，ClientHello 和 ServerHello 提供建立握手密钥所需的信息。双方派生握手密钥之后，服务端发送的 EncryptedExtensions、Certificate、CertificateVerify 和 Finished 等消息通常已经受到握手密钥保护。

CertificateVerify 用于证明服务端持有证书所对应的私钥，并将证明与本次握手联系起来。Finished 则用于验证握手记录及相关密钥。客户端也会发送自己的 Finished。这里不包含可选客户端证书认证、恢复握手及早期数据等分支。

临时密钥协商还可以在满足相应条件时提供前向保密性（Forward Secrecy）：长期身份私钥日后泄露，不必然导致此前记录的会话内容被解密。这依赖临时秘密、协议模式及实际实现的安全处理。

第四步：保护应用数据

在正常完成相应握手之后，双方可以利用派生得到的密钥，通过认证加密保护 HTTP 等应用数据。

HTTP 仍然负责请求方法、状态码和业务消息的语义。TLS 提供的是通信保护机制，不会代替服务端的身份授权、数据验证或数据库事务。

TLS 1.3 也支持其他握手方式，例如使用先前建立的预共享密钥。HTTP/3 则通过集成 TLS 1.3 的 QUIC 机制提供安全传输，不能简单理解为所有 HTTPS 都在普通 TCP 连接上运行。

HTTPS 的保护在哪里结束

如果网站在反向代理或 CDN 入口终止 TLS，入口可以处理已经解密的 HTTP 信息。入口到后端是否继续采用受保护连接，取决于部署配置。

HTTPS 也不能阻止网站自身在获得数据后错误保存或泄露数据，不能消除钓鱼网站，更不能保护已被控制的终端。

通常仍会有部分网络元数据暴露，例如通信对端地址及流量特征。域名信息的可见范围还取决于 DNS 和握手保护方式等条件。

我们现在终于可以完整理解 HTTPS 在系统中的位置：它保护通信路径上的特定边界，而不是整个应用所有层次的安全保证。
