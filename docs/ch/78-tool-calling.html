第十部 · AI 与 Agent

AI 怎样从生成文字发展到真正操作软件

假设我们要求模型检查报名系统的测试是否通过。它可以生成一条运行测试的命令，但写出命令与实际执行命令是两个不同的事实。

第三部已经知道，程序需要在相应运行环境中才能启动。第八部也已经知道，测试结果需要来自真实执行。

语言模型本身生成的文字不能证明某个程序已经运行。

工具是具有明确接口的能力

我们可以为 AI 应用提供一个软件接口，例如读取文件、查询数据库或者运行允许的测试命令。

这个接口需要规定工具名称、输入参数、返回结果和权限范围。它与第四部介绍的 API 具有直接联系。

模型可以根据任务提出使用某个工具的请求。应用负责解析该请求，检查相关限制，在允许时执行操作，再将结果提供给模型。

这种将模型生成的结构化请求连接到外部执行能力的方式，通常称为工具调用（Tool Calling）。

一次工具调用怎样发生

考虑一个虚构的只读工具 read_file。它接受一个项目内路径。

模型可能提出以下结构化请求：

{
  "tool": "read_file",
  "arguments": {
    "path": "README.md"
  }
}

这只是教学请求格式，不代表某个实际模型 API 的标准格式。

应用必须先检查路径是否位于允许访问的范围内。若允许，再读取文件并返回真实内容。

模型获得内容后可以继续分析。如果工具返回文件不存在，它就不能将自己猜测的 README 内容当成实际读取结果。

工具参数也需要独立验证

工具可以声明参数的类型与范围，但模型生成符合格式的请求并不等于操作已经获得授权。

下面用一个仅包含虚构内容的内存字典模拟只读工具。它不读取真实文件：

documents = {"README.md": "registration demo"}

def read_file(arguments):
    if not isinstance(arguments, dict):
        return {"error": "invalid arguments"}
    path = arguments.get("path")
    if not isinstance(path, str) or path not in documents:
        return {"error": "not allowed"}
    return {"content": documents[path]}

assert read_file({"path": "README.md"})["content"] == "registration demo"
assert "error" in read_file({"path": "private.txt"})

这里通过固定允许列表约束读取范围。真实文件工具还需要依据实际文件系统和权限模型处理路径解析、符号链接及访问范围，不能简单照搬这个内存模型。

工具结果还应区分成功、错误、超时与部分完成，尤其不能把工具接受请求当作操作成功的证据。

工具声明与实际能力不能混为一谈

告诉模型存在一个 run_tests 工具，不等于工具一定能够正常使用。执行环境可能缺少依赖、没有权限，或者目标项目根本没有测试配置。

工具调用也可能超时、返回部分数据或执行失败。

因此，应区分模型提出的动作、宿主是否接受请求、工具是否成功执行，以及返回信息能够支持什么结论。

对于软件开发，生成补丁、写入文件、提交 Git 和部署到生产环境也是不同的操作。每一步都有自己的权限与验收条件。
