第一部 · 计算机技术基础

第 12 章 与 AI Agent 协作：从需求到交付

使用 Agent 开发软件，需要理解它的执行能力、权限边界以及软件工程的验证方法。

一、从对话模型到 Agent

大语言模型（Large Language Model，LLM）根据输入上下文生成输出。Agent 则是一类将模型与工具、任务状态和执行流程结合的系统。它可以读取文件、调用 API、运行测试，或者根据工具返回的结果继续处理任务。具体能力取决于产品提供的工具和授权，而不是模型名称。

工具调用（Tool Calling）通常由模型提出结构化调用请求，由宿主程序检查参数与权限并执行，再将结果交给模型。模型生成调用请求并不等于操作已经执行成功。需要检查真实工具返回值、文件变化、退出码以及外部系统状态。

模型上下文协议（Model Context Protocol，MCP）是一种连接 AI 应用与外部工具及资源的协议。它不是模型本身，也不意味着接入的工具自动具备所有权限。

二、上下文与项目状态

上下文窗口（Context Window）限定模型一次推理能够处理的输入及生成内容的范围，通常以 Token 衡量。长会话可能被截断或压缩，但上下文容量不是任务复杂度的唯一限制。需求冲突、缺少证据、工具权限不足和模型判断错误同样会导致失败。

项目文件、Git 提交、测试结果和任务记录可以提供独立于聊天记录的持久化状态。应将关键决策写入项目文档，而不是依赖 Agent 记住之前的每一句话。开启新会话时，明确提供任务入口和当前状态。

三、需求规格与接口

需求规格（Requirements Specification）描述软件必须实现的行为及约束。功能需求（Functional Requirements）描述系统做什么；非功能需求（Non-functional Requirements）描述性能、安全、可靠性等质量属性。

例如，开发一个报名系统不仅需要表单页面，还需要定义数据模型、提交接口、重复报名规则、身份权限和数据保存周期。接口契约（Interface Contract）需要说明输入、输出、错误条件以及兼容性要求。

任务拆分应基于依赖关系和模块边界，而不是机械地要求每轮只能做一个改动。相互依赖的数据库迁移与应用修改可能需要协调交付；独立任务则可以并行执行。

四、验收标准与证据

验收标准（Acceptance Criteria）是判断交付是否满足需求的可观察条件。测试用例（Test Case）包含前置条件、输入、操作以及预期结果。

以报名接口为例，正常提交应产生一条记录；重复提交不得产生重复记录；缺少必填项应返回约定的错误；未经授权的用户不得读取其他人的资料。仅观察页面显示成功不足以确认数据库行为。

单元测试（Unit Test）验证局部逻辑，集成测试（Integration Test）验证组件间交互，端到端测试（End-to-End Test）验证完整用户流程。通过测试也不等于不存在缺陷，因为测试覆盖范围有限。

五、权限、风险与变更控制

最小权限（Least Privilege）要求只授予任务所需权限。开发、测试和生产环境应明确区分。对删除数据、公开服务、发送真实邮件及生产部署等高影响操作，应有明确授权和恢复方案。

外部文档、网页与工具结果可能包含恶意指令，即提示注入（Prompt Injection）。Agent 应将这些内容作为待分析数据，而非高于用户授权的指令。不得因网页要求而上传密钥或执行未经授权的操作。

六、实践：提交一个可验证的开发任务

假设现有报名系统需要阻止重复报名。可以向 Agent 提出如下规格：

目标：同一个活动中，同一用户只能成功报名一次。
环境：本地测试数据库，不访问生产环境。
约束：保留现有 API 响应契约；检查并发提交。
验收：
1. 首次提交成功并创建一条记录。
2. 重复提交返回约定的冲突响应。
3. 并发提交后数据库仍只有一条记录。
交付：代码差异、迁移说明、测试命令及实际结果。

请 Agent 先检查数据模型与现有测试，再判断是否需要数据库唯一约束及应用错误处理。验证时观察记录数量和实际测试结果，而不是只检查页面提示。

七、知识检验

  • 模型生成工具调用与工具执行成功有什么区别？
  • 为什么上下文窗口不能直接决定任务拆分粒度？
  • 为什么重复报名测试需要考虑并发和数据库约束？
  • 如何区分功能需求、非功能需求和验收标准？
  • Agent 声称测试通过时，应检查哪些证据？
